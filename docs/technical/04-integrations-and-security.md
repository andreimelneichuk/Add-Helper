# Интеграции и безопасность

## Яндекс Директ

Сервис работает с Директом через собственный тонкий клиент на `httpx`, без сторонних SDK. Клиент включается флагом `DIRECT_ENABLED`, адреса API задаются конфигурацией, так что для проверок подставляется песочница или имитация.

**Структура рекламы.** Для направления создаётся единая перфоманс-кампания (API `v501`, `UnifiedCampaign`) со стратегией «максимум кликов» и лимитом на период. Внутри неё группы объявлений с поисковыми фразами по услуге и районом, автотаргетингом и объявлениями с картинками.

**Что учтено в клиенте** (всё проверено на настоящем кабинете и записано как образец для тестов):

- **Ошибки.** Директ отвечает HTTP 200 даже с ошибкой, она лежит в теле ответа. Клиент разделяет четыре вида: авторизация, нехватка баллов, отказ по данным и сбой.
- **Повторы.** Чтение повторяется при сбоях сети и кодах «занято». Изменение клиент повторяет только если соединения не было: вызов `add` мог примениться до потери ответа, поэтому остальное доводит журнал после чтения состояния.
- **Баллы API.** Клиент запоминает остаток баллов по логину из заголовка ответа и отдельным видом ошибки сообщает об их нехватке. Не более двух запросов одновременно, до трёх попыток с растущей паузой.
- **Две своих автостратегии сразу Директ не принимает** (проверено на настоящем кабинете 2026-11-05), поэтому лимит ставится на одну сторону: поиск или сети, по выбранному размещению. Вторая сторона либо выключена, либо при размещении «поиск и сайты» идёт по стратегии первой.
- **Расписание применяется с задержкой.** `Campaigns.get` сразу после изменения отдаёт старое значение. Журнал не закрывает запись, пока чтение не совпало с планом.
- **Время.** Границы суток и недель считаются по Москве: Директ использует московское время, хранится всё в UTC.
- **Статистика** берётся из отчётов `Reports` (кампании, объявления, счёт). Деньги в отчётах приходят из площадки, пересчёт их не подменяет.

**Токены.** Каждый подключённый кабинет хранится зашифрованным (AES-256-GCM), ключи версионируются и меняются без остановки. Если один кабинет подключён к нескольким бизнесам одного владельца, токен шифруется отдельно для каждого, а обновление синхронно обновляет все копии.

## Яндекс ID и подключение кабинета

Вход идёт по OAuth 2.0 с одноразовым `state`, привязанным к браузеру, и PKCE (`S256`). Токен сессии случайный, в базе только его хэш, отзыв работает на сервере. Куки сессии `HttpOnly`, `Secure`, `SameSite=Lax`. Каждый изменяющий запрос требует токена CSRF, сравнение через `compare_digest`.

Параметры приложений Яндекса задаются конфигурацией, поэтому заказчик подключает свои приложения без изменения кода.

## Яндекс Метрика

Сервис проверяет, что на сайте стоит код счётчика: воркер скачивает главную страницу и ищет код. Отсутствие счётчика не блокирует запуск: кампания создаётся без него, а сводка готовности предупреждает, что обращения могут не учитываться. Создание счётчика и целей через API не подключено.

Проверка качества данных рассчитана на перекрёстную сверку кликов Директа с визитами Метрики за московские дни: если визитов намного меньше кликов, выводы об эффективности не делаются. Порт чтения визитов описан, но реализации для Метрики пока нет, поэтому визиты сейчас считаются неизвестными, и эта сверка не работает. Остальные проверки качества данных работают.

## Маркировка рекламы по 347-ФЗ

Сервис реквизиты рекламодателя не запрашивает и не хранит как основной источник: ИНН, тип рекламодателя, наименование и ОКВЭД лежат в кабинете Директа, и сервис их оттуда читает (`Clients.get`). Токен и пометку «Реклама» присваивает сам Директ.

- Перед запуском сводка готовности проверяет, что в кабинете реквизиты заполнены. Если их нет, запуск блокируется с понятным сообщением: рекламодателю нужно заполнить их в кабинете Директа.
- В интерфейсе реквизиты показываются в маске (последние цифры ИНН и телефона).
- Запасной путь: если реквизитов в кабинете нет, владелец может ввести их в мастере, и сервис передаст их в Директ записью журнала до создания кампаний. В этом случае они хранятся зашифрованными, а в журнале остаются только тип, конец ИНН и ОКВЭД.

## Модели

Языковые модели подключены через один клиент в формате OpenAI Chat Completions. Провайдера определяют адрес, ключ и имя модели из конфигурации. Тот же формат принимают OpenRouter, Yandex AI Studio и большинство других провайдеров, а несовместимый провайдер подключается через шлюз, без нового кода. Отдельно задаются модели писателя, судьи и рецензента, картинок. Включение генерации изображений управляется переменной `IMAGE_GENERATION`.

## Безопасность

| Риск | Мера |
|---|---|
| Утечка токенов и реквизитов | Реквизиты для маркировки сервис читает из кабинета Директа и сам не хранит. Токены: AES-256-GCM, ключ вне базы. Шифртекст привязан контекстом к бизнесу и логину кабинета, поэтому подмена строки в базе не даёт расшифровать токен. В логи и модели секреты не попадают, в журнале хранится только конец ИНН |
| Подмена входа | Одноразовый `state` и PKCE (`S256`). Адрес возврата после входа берётся из закрытого списка, открытого перенаправления нет |
| Доступ к чужим данным | Каждый запрос ограничен `business_id` на уровне репозитория. На чужой бизнес сервис отвечает 404. Проверяется автотестами |
| Чтение сайтов (SSRF) | Только `http` и `https` на портах 80 и 443. IP проверяется при соединении, соединение идёт с проверенным адресом, поэтому перенаправление и смена DNS не ведут во внутреннюю сеть. До трёх страниц, 1 МБ на страницу, общий срок. Браузер для сайтов с генерацией скриптами не имеет собственной сети: все его запросы идут через тот же защищённый клиент |
| Инъекция команд через текст сайта | Текст сайта считается данными. Извлекатель возвращает только поля с дословной цитатой, остальное код отбрасывает. Модель не управляет деньгами |
| Злоупотребление без входа | Разбор сайта и написание объявлений до входа ограничены по сети и общим потолком в сутки, результат отдаётся только по ключу, который знает браузер |
| Загрузка фото | Проверка типа и размера, повторное кодирование изображения, хранение с согласием владельца |
| Расход на модели | Лимиты на бизнес в сутки: наборы объявлений, разборы сайта, сделанные сервисом фото |
| Веб-сервер | Наружу открыты только `/api/*`, `/healthz` и файлы интерфейса. `/docs` и `/openapi.json` закрыты. Тело запроса до 1 МБ, CSP без внешних источников, HSTS, `nosniff`, заголовок `Server` убран. Проверяется скриптом `deploy/smoke.sh` при установке и на CI |
| Персональные данные | Данные хранятся в вашей базе; реквизиты для маркировки лежат в Директе, а если введены вручную, шифруются; в модели они не передаются; заказчик как оператор данных сам публикует политику обработки и получает согласия |

Перед выпуском проведён аудит по коду и тестам: каждый изменяющий маршрут требует сессии и CSRF, куки защищены, в логи пишется только тип ошибки. Зависимости проверяются командами `pip-audit` и `npm audit` перед выпуском.

## Что вне границ ответственности сервиса

- **Юридическая проверка текстов.** Объявления проверяются на выдуманные факты, но не на соответствие закону о рекламе.
- **Политика обработки персональных данных и уведомление Роскомнадзора** остаются обязанностью заказчика как оператора данных.
- **Отдельный сетевой контур для воркера**, который читает сайты, пока не настроен: защита держится на проверке IP при соединении.
