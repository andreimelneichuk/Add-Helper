# Эксплуатация

Этот документ даёт обзор. Пошаговая установка на сервер и настройка приложения Яндекса описаны в [README](../../README.md#часть-2-установка-на-свой-сервер).

## Что нужно для работы

| Что | Требование |
|---|---|
| Сервер | Linux с Docker и Compose. Для старта 2 vCPU, 4 ГБ RAM, 40 ГБ SSD. Размещение в РФ из-за персональных данных |
| Домен | A-запись на сервер, открытые порты 80 и 443 |
| Приложение Яндекса | Для входа и подключения кабинета: идентификатор и секрет |
| Доступ к Директ API | Заявка на полный доступ для рекламного логина |
| Ключ языковой модели | Любой провайдер в формате OpenAI Chat Completions |
| Почтовый ящик SMTP | Для писем о тревогах (необязательно) |
| Telegram-бот | Для сообщений о тревогах (необязательно) |

## Состав и запуск

```bash
make setup                                   # зависимости и сервис в Docker (разработка и проверка)
docker compose up -d --build                 # база, миграции, приложение, воркер
docker compose --profile production up -d    # то же и веб-сервер Caddy с сертификатом
```

Службы Compose: `db` (PostgreSQL 16), `migrate` (разовая, применяет миграции), `app` (API и интерфейс), `worker` (фоновые задачи в очередях `budget`, `creatives`, `notifications`), `caddy` (только на сервере). Приложение стартует после успешных миграций, а `app` и `worker` перезапускаются сами.

Образ собирается в два этапа: сначала интерфейс, затем Python-образ с headless Chromium для чтения сайтов, которые рисует скрипт. Процесс внутри работает от непривилегированного пользователя.

## Настройка

Все настройки задаются переменными окружения, образец — файл `.env.example`:

| Группа | Переменные |
|---|---|
| База | `DATABASE_URL` (для управляемой базы), `POSTGRES_PASSWORD` |
| Секреты | `TOKEN_ENCRYPTION_KEYS` (список ключей, новый первым) |
| Адрес | `PUBLIC_BASE_URL`, `DOMAIN` |
| Яндекс | `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET` и аналогичные для подключения кабинета |
| Директ | `DIRECT_ENABLED`, `DIRECT_API_URL`, `DIRECT_LIVE_URL` |
| Модели | `TEXT_MODEL_BASE_URL`, `TEXT_MODEL_API_KEY`, `TEXT_MODEL_NAME`, `JUDGE_MODEL_NAME`, `REVIEW_MODEL_NAME`, `IMAGE_GENERATION` |
| Уведомления | `SMTP_*`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_NAME` |
| Автопилот | `AUTOPILOT_AUTO_ALLOWED` (режим «Сам», по умолчанию `false`) |

Пороги правил (бюджет, оценка, политика, генерация) лежат не в переменных, а в версионируемых файлах правил внутри проекта. Версия правил записывается в каждое решение, поэтому можно проверить, по каким правилам оно принято.

## Команды оператора

| Команда | Назначение |
|---|---|
| `adhelper check` | Проверить настройки, базу и очередь задач; выводит предупреждения о зависших задачах |
| `adhelper emergency-stop --business <id>` | Приостановить всю рекламу бизнеса через журнал |
| `adhelper stats-sync` | Обновить отчёты кампаний и объявлений из Директа |
| `adhelper simulate --business <id> --rules A --against B` | Сравнить две версии правил автопилота на истории кабинета, только чтение |
| `adhelper shadow-report` | Недельный отчёт теневого периода автопилота |
| `adhelper trust` | Лестница доверия: что автопилоту разрешено самому |
| `adhelper demo-seed` | Демо-кабинет для просмотра интерфейса, только на локальной базе |

Запускаются командой вида `docker compose exec app adhelper check`.

## Наблюдение

- **`/healthz`** — проверка работоспособности для внешнего монитора.
- **Логи** — `docker compose logs`, секреты маскируются, ошибки пишутся с типом.
- **Тревоги владельцу** — письмо и Telegram о приближении к лимиту, остановке по бюджету, расхождении со счётом, нулевом балансе, недоступности Директа, отказе модерации и об автооткате автопилота. Раз в сутки приходит сводка «что запущено».
- **Журнал изменений и решений** показывает, что сделал сервис и почему.

Служебной панели администратора и писем администратору о сбоях нет: внешний монитор подключается оператором. Фоновые задачи сообщают о себе: воркер записывает пульс каждую минуту, и `adhelper check` предупреждает, если пульса нет больше 5 минут.

## Резервные копии

| Команда | Что делает |
|---|---|
| `make backup` | Кладёт копию базы в `backups/` и удаляет копии старше `BACKUP_KEEP_DAYS` (по умолчанию 14) |
| `make restore-check` | Восстанавливает последнюю копию во временную базу и сверяет схему и журнал, рабочую базу не трогает |

Копии нужно запускать ежедневно по расписанию и уносить за пределы сервера. Восстановление: остановить `app` и `worker`, выполнить `pg_restore`, запустить `adhelper check`. Это заменяет рабочие данные.

## Обновление

```bash
git pull
docker compose up -d --build
```

Миграции базы обратно совместимы в пределах версии: предыдущая версия приложения продолжает работать на новой схеме. Миграции применяются при старте. Новая версия правил автопилота сначала работает в теневом режиме.

## Смена ключа шифрования

Новый ключ добавляется первым в `TOKEN_ENCRYPTION_KEYS`: новые записи шифруются им, а старые читаются прежним. Команды перешифровки пока нет, поэтому старый ключ нужно сохранять, пока не переподключены все кабинеты. Потеря ключа делает токены нечитаемыми, поэтому хранить его нужно отдельно от копий базы.

## Автоматические проверки качества

На каждое изменение в репозитории запускается конвейер CI:

| Проверка | Что проверяет |
|---|---|
| Линтинг и типы | `ruff format`, `ruff check`, `mypy`, границы модулей (`import-linter`) |
| Фронтенд | Проверка типов TypeScript и тесты интерфейса (Vitest) |
| Тесты бэкенда | Около 1700 тестов на настоящем PostgreSQL, включая свойства бюджета (`hypothesis`) и сбои в журнале |
| Интеграция | Сборка образа, команда `adhelper check` в образе, резервная копия и восстановление, веб-сервер Caddy и защитные заголовки |

Дополнительно есть сквозные тесты интерфейса в браузере (`make e2e`) и набор `evals` для платных замеров качества моделей.
