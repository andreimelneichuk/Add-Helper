## 1. Модульный монолит

**Выбрано.** Один Python-проект, один образ, модули с жёсткими границами, проверяемыми линтером.

**Альтернативы.** Микросервисы; единый «комок» кода без границ.

**Почему.** Заказчик разворачивает сервис сам и без отдельной команды эксплуатации: несколько сервисов умножили бы сложность установки, мониторинга и обновления. Масштаб первых лет невелик. Но границы модулей при этом не размыты: правила `api → application → domain` и «домен не знает про HTTP, SDK и ORM» проверяются автоматически на каждом изменении (четыре контракта `import-linter`). Любой модуль можно вынести в отдельный сервис, не переписывая его логику.

## 2. PostgreSQL как единственное хранилище и очередь

**Выбрано.** PostgreSQL 16 для данных, журнала и очереди фоновых задач (Procrastinate). Отдельного брокера нет.

**Альтернативы.** Redis или RabbitMQ для очереди; отдельное хранилище для журнала.

**Почему.** Задача ставится **в той же транзакции**, что и данные: невозможна ситуация «запись сохранена, а задача потерялась» или наоборот. Это напрямую следует из приоритета восстановимости. Меньше компонентов для установки. Транзакции и триггеры PostgreSQL нужны журналу: именно триггер запрещает менять записанное «до».

**Цена решения.** Очередь на базе данных медленнее специализированного брокера. Для нашей нагрузки (десятки задач в минуту) это несущественно.

## 3. Единый журнал изменений

**Выбрано.** Всё, что меняет Директ, проходит один путь: политика, журнал со снимком «до», исполнитель, чтение результата. Включая откат и действия владельца.

**Альтернативы.** Каждый модуль вызывает площадку сам; журнал как побочный лог.

**Почему.** Один путь даёт одну точку, где проверяются бюджет, частота и конфликты, и один источник истории. Объяснение «что сделано, почему, с цифрами, как отменить» и откат строятся на одном механизме, а не повторяются в каждом модуле. Журнал только дополняется: откат создаёт новую запись, а не правит старую, и триггер PostgreSQL защищает сохранённое «до».

**Следствие.** У многих методов Директа нет идемпотентности. Поэтому повтор всегда начинается с чтения фактического состояния, а созданные объекты получают нашу метку в названии: после сбоя их можно найти и не создать дубль.

## 4. Бюджет защищён на стороне площадки

**Выбрано.** Лимит на период с датой окончания и выключенным автопродлением задан внутри Яндекса. Поверх него шесть слоёв наблюдения.

**Альтернатива.** Держать лимит только в сервисе и останавливать кампании, когда расход приближается к границе.

**Почему.** Сервис может упасть, потерять связь, получить задержанную статистику. Если защита существует только в сервисе, любой такой сбой оставляет бюджет без охраны. Защита на стороне площадки работает независимо от нас. Остальные слои охраняют от того, что лимит выставлен неверно. Этот выбор приводит к жёсткому правилу: при нехватке баллов API контроль бюджета важнее оптимизации. См. [защиту денег](02-money-safety.md).

**Что проверили в Директе.** Устаревший `DailyBudget` не используется, а лимит по периоду (`CustomPeriodBudget`) вместе с недельным задать нельзя. Две автостратегии сразу Директ не принимает, поэтому лимит ставится на одну сторону.

## 5. Деньги в целых числах

**Выбрано.** Микроединицы площадки при хранении, базисные пункты для долей, округление только при показе.

**Альтернативы.** Числа с плавающей точкой; `decimal`.

**Почему.** Накопленные ошибки округления в деньгах недопустимы, а сверка со счётом требует точных чисел. Целые числа дают точное равенство при сравнении с данными площадки. Деньги в отчётах берутся из отчётов площадки, а наш пересчёт их не подменяет. Округление всегда в сторону безопасности: рабочий бюджет вниз, расход и прогноз вверх.

## 6. Решения о деньгах принимает код, а не нейросеть

**Выбрано.** Деньгами управляют версионируемые детерминированные правила. Нейросеть пишет тексты и разбирает просьбы из чата в закрытый набор команд.

**Альтернатива.** Агент на основе языковой модели, который сам решает, что менять в кампаниях.

**Почему.**
- Решение должно быть воспроизводимым: по тем же данным те же правила дают тот же результат. Это позволяет разбирать спорные случаи и проверять новую версию на истории (`adhelper simulate`).
- Нейросеть может ошибиться в числе, выдумать факт или выполнить инструкцию из текста чужого сайта. Для текстов это ограничивается проверками, для денег такой риск неприемлем.
- Свои ошибки у модели измерить сложно, у кода просто: тесты и свойства.

Если задача требует участия модели рядом с деньгами, она получает роль «рецензента»: может только остановить автоматическое действие и передать его владельцу, но не разрешить ничего сверх политики.

## 7. Байесовская оценка вместо порогов

**Выбрано.** Доля обращений по объявлению оценивается Beta-Binomial моделью, а решение принимается по ожидаемой потере в рублях при ожидании.

**Альтернативы.** Фиксированные пороги («меньше N обращений при расходе M — остановить»); большие модели машинного обучения.

**Почему.** У малого бизнеса десятки кликов и единицы обращений в неделю. Фиксированный порог на таких числах реагирует на случайность: три клика без заявок для него уже «плохое объявление». Байесовская модель честно показывает неопределённость и не требует большого обучающего набора. Ожидаемая потеря отвечает на вопрос владельца: «сколько мы потеряем, если подождать, и стоит ли ждать». Оценка детерминирована: интегрирование по сетке из 2000 точек, без случайных чисел, результат воспроизводим. Тяжёлым моделям на таком объёме данных нет применения: они дали бы ложную точность.

**Как вводится.** Новая версия оценки сначала работает в теневом режиме рядом с рабочей. См. решение 9.

## 8. A/B-тест внутри группы объявлений

**Выбрано.** Два варианта показываются одновременно в одной группе, Директ сам делит показы, проигравший ставится на паузу.

**Альтернативы.** Встроенные эксперименты Директ Про; поочерёдное включение вариантов по дням.

**Почему.**
- Эксперименты Директ Про в API не найдены, а создание сегментов через Аудитории закрыто.
- Чередование по дням отвергнуто после анализа: ежедневные паузы сбивают обучение автостратегии и запускают разогрев заново. При десятке кликов в день каждый вариант копил бы данные через день, то есть вдвое медленнее.
- Тест внутри группы даёт одну аудиторию, один аукцион и одни дни. Данные копятся вдвое быстрее, обучение автостратегии не теряется.

**Ограничение.** Ротация Директа делит показы неравномерно. При сильном перекосе тест честно заканчивается выводом «данных мало», а не случайным победителем.

## 9. Режимы «Следит», «Предлагает», «Сам» и ворота включения

**Выбрано.** Автопилот имеет три положения, и «Сам» по умолчанию закрыт. Включается он по ступеням: теневой период, подтверждённые пороги, лестница доверия, письменное согласие, малая кампания.

**Альтернатива.** Сразу включить полную автономию.

**Почему.** Ошибка автономного режима стоит денег клиента, а пороги оценки ещё не откалиброваны на реальных данных. Теневой режим позволяет собрать «что сделала бы система» и сравнить с фактическим исходом без риска. Лестница доверия открывает классы действий по одному, начиная с самого безопасного (пауза объявления). Автооткат и предохранители (два автоотката за 14 дней возвращают режим «Предлагает») ограничивают цену ошибки.

## 10. Факты в рекламе только из профиля

**Выбрано.** Цены, скидки, отзывы и проверяемые свойства («свежий», «натуральный») допускаются в объявлении, только если они есть в подтверждённом профиле. Субъективные оценки и угол подачи свободны.

**Альтернатива.** Позволить модели писать свободно и проверять постфактум.

**Почему.** Выдуманная скидка или цена в рекламе — ошибка, которая стоит клиенту денег, доверия и возможных претензий. Поэтому факт любого вида проходит три фильтра: код сверяет ключи и числа с профилем, вторая модель ищет утверждения без опоры, а при сомнении объявление снимается. При этом запрет всего, что не из профиля, привёл бы к шаблонным текстам: творческая свобода оставлена там, где она не создаёт ложных обещаний. Факты в профиль попадают только с дословной цитатой источника и после подтверждения владельцем.

## 11. Писатель и судья от разных производителей

**Выбрано.** Модель, которая пишет текст, и модель, которая его проверяет, взяты у разных разработчиков. Расчёт выпуска идёт по формуле, которая учитывает ошибку обеих.

**Почему.** Модели одного семейства склонны повторять одинаковые ошибки и одинаково пропускать их. Ворота выпуска (верхняя граница доли выдумок не выше порога при уверенности 95%) считаются на замороженном наборе `test`, на котором промпты не подгоняются. Для судьи отдельно замерена доля пропусков, а для писателя доля снятых объявлений. Результат опубликован: на сегодня верхняя граница 0,87% при пороге 3%.

## 12. Один клиент для всех языковых моделей

**Выбрано.** Один клиент формата OpenAI Chat Completions. Провайдера определяют адрес, ключ и имя модели.

**Альтернатива.** Отдельный клиент на каждого провайдера.

**Почему.** Этот формат принимают Yandex AI Studio, OpenRouter и большинство остальных провайдеров. Смена провайдера или модели — это изменение конфигурации. Провайдер без такого формата подключается через шлюз, а не новым кодом. Это снижает зависимость заказчика от одного поставщика и упрощает замену моделей при изменении цен или доступности из РФ.

## 13. Узкие порты площадки

**Выбрано.** Не один общий интерфейс «рекламная площадка», а узкие порты по задачам (`BudgetPlatform`, `AdPublisher`, `AdControl` и другие) на языке нашего домена.

**Почему.** Страж бюджета не должен знать, как публикуются объявления, а публикация не должна знать, как читается расход. Узкие порты можно заменить по одному, их легко подделать в тестах. Особенности Директа (версии `v5` и `v501`, формат денег, коды ошибок) остаются в адаптере: VK Реклама потребует нового адаптера, а правила автопилота и бюджета не изменятся.

## 14. Правила в версионируемых файлах

**Выбрано.** Пороги и параметры лежат в файлах правил с номером версии (`budget-1`, `autopilot-3`, `policy-1`, `creatives-3` и другие). Каждое решение записывает версию правил и входные данные.

**Почему.** Порог, зашитый в код, трудно менять и невозможно пересчитать задним числом. Файл правил позволяет заменить версию без правки кода, сравнить две версии на истории кабинета и показать в журнале, по каким именно правилам принято решение. Правила проверяются при загрузке: неверный файл не запускает работу, а закрывает ворота автопилота.

## 15. Тесты на поддельной площадке и записанных ответах

**Выбрано.** Логика денег проверяется на поддельной площадке, которая реализует те же порты, что настоящий адаптер. Клиент Директа проверяется на ответах, записанных с настоящего кабинета.

**Почему.** Сбои, обрывы связи и повторы нельзя вызвать на настоящем Директе по требованию, а на поддельной площадке можно: падение в семи точках журнала, неполный ответ, ответ со вторым вызовом. Свойства бюджета проверяются на случайных данных (`hypothesis`). Каждая ошибка получает воспроизводящий тест до исправления. Записи ответов очищаются от токенов, а формат сверяется с документацией Директа.

**Порядок для клиента Директа.** Сначала реальный вызов на малой кампании, затем тест на записанном ответе. Так в тестах лежит то, что Директ действительно отвечает, а не то, как мы его представляли по документации.

## 16. Собственный клиент Директа

**Выбрано.** Тонкий клиент на `httpx` вместо готового SDK.

**Почему.** Директ отвечает ошибкой при коде 200, тело ошибки нужно разобрать и сопоставить с нашими понятиями (авторизация, баллы, данные, сбой). Правила повторов у чтения и записи разные: повторять запись вслепую опасно. Баллы API и ограничение числа одновременных запросов должны учитываться на уровне клиента. Готовый SDK скрывает эти детали, а нам нужен контроль над каждой.

## 17. Откуда берётся информация о площадке

**Выбрано.** Факты о Директе и других площадках собраны в исследовании с меткой достоверности: документация, вторичный источник, гипотеза, реальный вызов API.

**Почему.** API Директа менялся, а в октябре 2026 интерфейс был недоступен несколько дней. Проверенные вызовами факты (например, что две автостратегии не принимаются) отделены от предположений по документации. Новое поведение добавляется в исследование после реального вызова. Запуск на настоящем кабинете и трата денег согласуются с владельцем проекта.

## 18. Развёртывание через Docker Compose

**Выбрано.** Docker Compose с готовым образом, Caddy для сертификата и резервной копией одной командой.

**Альтернативы.** Kubernetes; установка пакетами на сервер.

**Почему.** Заказчик устанавливает сервис сам, поэтому сценарий установки должен быть одним. Compose поднимает базу, миграции, приложение и воркер в нужном порядке, а Caddy выпускает сертификат сам. Тот же образ работает на хостинге с управляемой базой данных: там API и воркеры запускаются одним контейнером. Установка и восстановление из копии проверяются на каждом изменении в CI.

**Что пока не проверено.** Установка на отдельный сервер с собственным доменом по инструкции ещё не выполнялась.
