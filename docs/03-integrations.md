# Интеграции

Подтверждённые факты и ссылки находятся в [исследовании](00-research.md). Здесь — как мы их используем. `S1`–`S11` — открытые проверки из того же документа. Названия полей перед реализацией сверяются с актуальной документацией.

## 1. Яндекс ID

| Поток | Права | Назначение |
|---|---|---|
| Вход | `login:info`, `login:email` | Идентификация пользователя |
| Подключение кабинета | `direct:api`, `login:info` | Работа с рекламой; логин кабинета. `metrika:read` и `metrika:write` добавим вместе с адаптером Метрики, пока код статистики проверяется скачиванием страницы |

- Параметры приложения: `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `PUBLIC_BASE_URL`. Менять код не нужно. Адреса Яндекс ID (`YANDEX_OAUTH_URL`, `YANDEX_LOGIN_URL`) тоже задаются конфигурацией: стенд e2e подставляет свой строгий сервер `/stand-yandex` (PKCE, одноразовый код, секрет приложения), и вход с подключением кабинета проходят тем же кодом, что в работе.
- Клиент `accounts/adapters/yandex_oauth.py` написан по документации, реальным вызовом не проверен (V1). Обмен кода: `POST {oauth}/token` формой с `code_verifier`, `client_id`, `client_secret`; профиль: `GET {login}/info?format=json` с `Authorization: OAuth <токен>`. Ответ 5xx и сбой сети — «Яндекс недоступен», 400/401 — «нужен новый вход». Код, токены и секрет в ошибки не попадают.
- При подключении используем `force_confirm`, чтобы пользователь мог выбрать другой логин.
- Токен обновляется при обращении: `TokenVault` берёт `refresh_token`, если срок доступа подходит к концу; при отказе кабинет переходит в `needs_reconnect`. Задачи `tokens.refresh` по расписанию и тревоги владельцу об истёкшем доступе пока нет, они появятся с клиентом Директа (T5, `S10`).
- Для владельца «создать кабинет» и «подключить кабинет» — одна кнопка «Подключить кабинет» (решение владельца проекта, 2026-11-02). Согласие OAuth ещё не значит, что у логина есть рабочий Директ. После возврата сервис читает клиента Директа: если кабинета нет или не приняты условия Директа, кабинет получает состояние «нужно завести кабинет» со ссылкой на Директ, а после возврата владельца сервис проверяет снова. Сейчас `complete_connect` сохраняет кабинет как подключённый без этой проверки; проверка появится вместе с клиентом Директа (T4–T5). Как Директ отвечает логину без кабинета и можно ли завести кабинет прямому рекламодателю через API, не проверено.
- Из мастера запуска подключение возвращает на `/?start` (`POST …/accounts/connect?then=start`, цель из того же списка, что у входа).
- Заголовок `Client-Login` передаётся, когда токен принадлежит представителю или агентству. Обычный сценарий: прямой рекламодатель.

## 2. Директ API

### Клиент

Клиент есть: `platforms/adapters/direct/` (задача 01, 2026-11-05). Включается флагом `DIRECT_ENABLED`, по умолчанию выключен до согласования боевого запуска; адреса `DIRECT_API_URL`, `DIRECT_LIVE_URL` (песочница — подменой адреса).

- **Транспорт** `DirectHttpClient` (`transport.py`): один на процесс, собственный тонкий клиент на `httpx`. Заголовки `Authorization`, `Accept-Language: ru`, `Client-Login`. Не более двух запросов одновременно. Остаток баллов из `Units` хранится по логину. Версии `v5`/`v501` заданы для каждого сервиса: кампании, группы и объявления идут через `v501`.
- **Ошибки.** Директ отвечает HTTP 200 с телом `error`. Разделены: авторизация (53, 54, 58, 513 и «нужен новый вход» из хранилища токенов), нехватка баллов (152), отказ по данным (ошибки в `*Results` и прочие коды), сбой. Все они для журнала — `PlatformUnavailable`: он перечитает площадку, повторит не больше `MAX_CHANGE_ATTEMPTS` раз и поднимет тревогу.
- **Повтор.** Чтение (`get`, `Reports`, `AccountManagement Get`) повторяется при 5xx/429 и кодах 52, 56, 506, 1000, 1001. Изменение транспорт повторяет только если соединения не было или Директ ответил «занят» (52, 56, 506): `add` мог примениться до потери ответа. Остальное доводит журнал после чтения.
- **Площадка** `DirectPlatform` (`platform.py`) реализует `BudgetPlatform`, `AdControl`, `TargetingControl`, `CampaignLauncher`, `AdPublisher`. `AdvertiserRegistry` (`Clients.update`, маркировка) ещё не реализован.
- **Токены.** `DirectPlatforms` (`factory.py`) берёт токен кабинета из хранилища своего бизнеса через `TokenVault`; тот же логин у чужого бизнеса токена не получит.
- **Лимит кампании** — `CustomPeriodBudget.SpendLimit`. Директ не принимает две автостратегии сразу: `WB_MAXIMUM_CLICKS` на поиске и на сетях вместе дают 4000 «Стратегии не совместимы» (проверено 2026-11-05). Поэтому сервис ставит стратегию с лимитом на одну сторону: на поиск для «поиск и сайты» и «только поиск» (сети тогда `NETWORK_DEFAULT` или `SERVING_OFF`), на сети для «только сайты». Лимит на поиске при `NETWORK_DEFAULT` — общий для кампании. Деление между сторонами (`split_limit`) и сумма частей при чтении остались для чужих кампаний с бюджетом на обеих сторонах. `Campaigns.update` с частичной стратегией (только `CustomPeriodBudget.SpendLimit`) принимается, даты периода не теряются. Кампания без лимита на период (чужая или с недельным бюджетом) для стража безлимитна, увеличения он не пропустит.
- **Расход кампании** — отчёт `CAMPAIGN_PERFORMANCE_REPORT` с начала её периода; расход кабинета — `ACCOUNT_PERFORMANCE_REPORT` за `ALL_TIME`. Оба с `IncludeVAT=YES`, `IncludeDiscount=NO` (гипотеза до `S3`). Момент данных считается на 3 часа раньше запроса (`REPORT_LAG`, до замера `S3`): страж добавит расход по скорости. Баланс — `AccountManagement` Live v4, сумма в рублях строкой переводится в микроединицы без округления.
- **Активна ли кампания:** состояния `ON` и `OFF` (может начать тратить), иначе нет.

Что записано с настоящего кабинета (`tests/platforms/direct/recorded/`): чтение пустого кабинета и сквозной прогон записи 2026-11-05 с согласия владельца — ЕПК с лимитом 300 ₽ на 6 дней, группа, объявления, смена лимита, расписание, регионы, приостановка объявления и кампании. Денег не тратили: счёт пуст, кампания `715840559` оставлена приостановленной. Что показал прогон:

- **Расписание применяется с задержкой:** `Campaigns.get` сразу после `update` отдаёт прежнее `TimeTargeting`, через минуту новое. Журнал не закрывает запись, пока чтение не совпало с планом, и дочитывает на следующем проходе.
- **`Href` хранится как отправлен**, вместе с меткой `ah_ad`; поиск объявления по метке работает.
- **Состояния:** новый черновик кампании — `State: OFF`, `Status: DRAFT`; приостановленный черновик объявления — `Status: UNKNOWN`, в `StatusClarification` текст вида «Ожидает модерации. Дата окончания кампании …». ID объявлений — большие int64.
- `Campaigns.get` возвращает в стратегии лишние поля (`BudgetType`, `BidCeiling: null`), `CounterIds` без счётчиков — `null`.
- Сверка `Reports` с кабинетом не проведена: расхода не было. Нужен показ с пополненным счётом.

### Создаваемая структура

```text
Единая перфоманс-кампания (направление) [UNIFIED_CAMPAIGN, v501]
├─ Стратегия: максимум кликов, затем максимум конверсий с оплатой за клики
├─ Лимит: CustomPeriodBudget (S2)
├─ Метрика: CounterIds, PriorityGoals
├─ Группа: поисковые фразы по услуге + район
│   └─ 2–3 ResponsiveAd: заголовки, тексты, изображения, ErirAdDescription
├─ Группа: автотаргетинг и широкие интересы
└─ Группа: аудитории по интересам и географии
```

**Как адаптер создаёт кампанию запуска.** `Campaigns.add` (`v501`, `UnifiedCampaign`): стратегия `WB_MAXIMUM_CLICKS` с `CustomPeriodBudget` (последний день периода по Москве, `AutoContinue: NO`, чтобы без сервиса показы остановились), ненужная сторона `SERVING_OFF`, `EndDate` кампании тот же; затем группа `UnifiedAdGroup` с регионом и объявления `TextAd`, отправленные на проверку. Повтор после сбоя ищет кампанию по метке в имени и доделывает только недостающее. Фраз и автотаргетинга группа пока не получает: покажется ли она без них, проверить в песочнице.

**Что создаёт запуск сейчас** (правила `campaigns/adapters/rules/launch-1.toml`, код `campaigns/domain/launch.py`). Это наш план; поля Директа для него проверит T5. Период 30 дней с московской полуночи. Рабочий бюджет равен месячному за вычетом резерва 10%, лимит каждой кампании округлён вниз до целых рублей, сумма лимитов не больше рабочего бюджета. От 30 000 ₽ в месяц, если каждая половина покрывает минимум, создаются две кампании: поиск и сайты Яндекса. Иначе одна, поиск и сайты вместе. Минимум площадки 50 ₽ в день, то есть 1 500 ₽ на кампанию за 30 дней, поэтому план бюджета начинается от 1 667 ₽ (`plan-2`). Регион берётся из города в адресе профиля, по целому слову. В кампании до 3 объявлений из выбранных в мастере, ссылка на сайт профиля и счётчики Метрики. Без сайта или без города запуск не начинается и говорит, что дописать.

### Распределение

Количество направлений зависит от бюджета. Значения — стартовые гипотезы, их калибруем на этапе 1 и на реальных кампаниях.

| Бюджет в месяц | Структура |
|---|---|
| Ниже рекомендованного минимума | Предупреждаем. Одна кампания, поиск и сети, один главный оффер |
| Средний | Две кампании: поисковый спрос и сети, чтобы разделять и переносить бюджет |
| Выше | Поиск, сети и отдельная география; добавляется VK Реклама, если подключена |

Рекомендованный минимум считаем для ниши и региона: на него должно приходиться достаточно кликов для первых выводов. Источники: `Keywords` и прогноз `CreateNewForecast`, если они подойдут.

Стратегии: стартуем с оплаты за клики. `PayForConversion` не используем: дневной расход может доходить до 100% лимита, а минимум бюджета равен 20 × CPA. `WbMaximumConversionRate` включается от 10 конверсий в неделю (рекомендация Яндекса), смена проходит через проверку бюджета.

| `Sitelinks`, `AdExtensions` | Быстрые ссылки и уточнения |
| `Bids`, `BidModifiers` | Корректировки, например время и устройства |

| `Changes` | Экономное чтение изменений |
| `Clients` | Лимиты, данные маркировки |
| `Dictionaries` | Регионы, минимумы валют |

**Где и когда показывать.** Порт `TargetingControl` в `campaigns/domain/ports.py` говорит нашими понятиями: дни недели, часы `[start, end)` и номера регионов. Адаптер Директа переводит расписание в `Campaigns.update` → `TimeTargeting` (коэффициент 100 в часы показа, 0 в остальные, `ConsiderWorkingWeekends: YES`), а регионы в `RegionIds` всех групп кампании. Читает обратно то же самое; расписание, которое нашими понятиями не выразить (разные часы по дням, коэффициенты кроме 0 и 100), читается как пустое, и журнал видит конфликт. Часовой пояс пока не задаётся: кампания живёт по Москве (по умолчанию Директа), для других поясов — доработка. Что проверить вызовом: `S12`.

### Модерация

Состояния `DRAFT → MODERATION → ACCEPTED | REJECTED`. При отказе система получает причину, просит у модуля креативов исправление не более двух раз, затем передаёт понятную просьбу владельцу. Новое объявление начинает показы только после проверки, предыдущее работает дальше.

Порт `AdPublisher` (`platforms/domain/ports.py`) содержит три операции: `find_ad` по метке, `create_ad` и `moderation` (итог проверки списка объявлений). Создание идёт через журнал (`create_ad`, цель `newad:ahc-<id>`). Директ не обещает идемпотентности `Ads.add`, поэтому перед повтором объявление ищется по метке. Текст причины отказа считается данными: код сводит его к закрытому набору `moderation-1`. Адаптер Директа хранит метку параметром ссылки `ah_ad=<метка>` (при чтении снимается), создаёт `TextAd` в первой группе кампании и сразу отправляет на проверку (`Ads.moderate`). `DRAFT`, `MODERATION`, `PREACCEPTED` — «на проверке», причина отказа — `StatusClarification`. Меняет ли Директ ссылку при сохранении и формулировки причин, нужно сверить в песочнице, достоверность — гипотеза.

### Сверка статистики

Критерий заказчика: статистика совпадает с кабинетом. Что для этого делаем:

1. Показываем расход только из `Reports`, а не из расчётов.
2. Используем те же параметры, что и кабинет: `IncludeVAT`, `IncludeDiscount`, модель атрибуции (`S3`). В интерфейсе подписываем «с НДС» или «без НДС».
3. Округляем только при показе и по правилам кабинета.
4. Ежедневно перечитываем последние дни и обрабатываем сигнал `STAT`. Метка «данные могут уточниться» держится три дня.
5. Автоматическая сверка суммы по кампаниям с итогом по аккаунту. Различие попадает в служебную панель.
6. Точные настройки отчёта, для сравнения с кабинетом, описаны прямо на экране статистики.

## 3. Метрика

1. Найти счётчик: показать существующие или создать новый.
2. Создать цели: заявка, клик по телефону, переход в мессенджер, запись. Часть целей срабатывает автоматически, а для заявок даём код `reachGoal`.
3. Проверка установки: загрузка страницы сайта и поиск кода, затем подтверждение поступления визитов через API. Первая часть сделана: воркер скачивает главную страницу (`site.tag_check`, правила `tag-1`, тот же защищённый загрузчик, что у разбора сайта) и ищет номер счётчика в разметке. Код через Tag Manager так не виден; владельцу это сказано, проверка визитами появится с доступом к API (V1).
4. Привязка к кампании через `CounterIds` и `PriorityGoals`.
5. Роли целей: `lead` (обращение) и `micro` (сигнал для коротких тестов, например переход к форме).
6. Отчёт по обращениям берётся из `Reports` (колонка конверсий по цели и модели) для сопоставления с расходом. Метрика используется как перекрёстная проверка (`S11`).
7. Визиты с рекламы для проверки качества данных автопилота (2026-11-05): порт `SiteVisits.ad_visits(counter, since, until)` за московские дни, счётчик берётся из последней проверки кода, нашедшей его (`SqlTagChecks.counter`). `None` значит «у Метрики нет данных за эти дни», сбой связи — `PlatformUnavailable`; в обоих случаях визиты неизвестны, а не ноль. Реализует пока только подставная площадка. Адаптер — отчёт Метрики `/stat/v1/data` с `ym:s:visits` и фильтром по источнику «Реклама Директа»: точное имя измерения и задержку данных сверить после доступа (V1).

Настройка должна укладываться в квоты: 200 запросов отчётов за 5 минут на пользователя, 5000 в сутки.

## 4. Маркировка

**Директ, прямой рекламодатель**
1. На шаге онбординга собираем тип, ИНН, наименование или ФИО, телефон для физлиц, ОКВЭД для организации и ИП. Сделано: шаг «Маркировка» мастера, `PUT /api/businesses/{id}/marking`.
2. Проверяем контрольную сумму ИНН и сохраняем в зашифрованном виде. Сделано: ИНН, имя и телефон хранятся шифртекстом с контекстом бизнеса, наружу уходит только конец ИНН. Принимает ли Директ ОКВЭД короче группы (`96.02`), не проверено (T5).
3. Отправляем `Clients.update` (`TinInfo`, `ErirAttributes`), перечитываем и сверяем. Сделано на подставной площадке: порт `AdvertiserRegistry`, запись журнала `set_advertiser` с целью `client:<логин>`. В журнале только тип, конец ИНН и ОКВЭД; реквизиты исполнитель расшифровывает при отправке. Запуск создаёт кампании, только когда журнал подтвердил маркировку чтением. Если данные изменились после записи, старая запись не отправляется. Воркер без ключа запись не трогает. Адаптер Директа и поля `TinInfo` — T5, достоверность — гипотеза.
4. В каждом объявлении заполняем `ErirAdDescription`: бренд, категория, суть. До 1000 символов.
5. Проверка данных блокирует запуск: «Без этих данных запустить рекламу нельзя по закону».
6. Показываем правило: один логин — один бизнес — один плательщик. Иначе требуется кабинет ОРД, и это выходит за рамки автоматического сценария.

Токен и пометка «Реклама» для Директа присваиваются автоматически. Проверим фактическое появление на боевом объявлении.

**VK Реклама:** порядок определяется проверкой `S9`.

## 5. VK Реклама (вторая площадка, этап 6)

- Адаптер тех же узких портов, что у Директа (`BudgetPlatform`, `PlatformGateway`, `AdControl`, `AdPublisher`, `TargetingControl`, `CampaignLauncher`, [архитектура](02-architecture.md)). Отображение: `AdPlan → кампания`, `AdGroup → группа`, `Banner → объявление`.
- Подключение. Предпочтительно OAuth сервисного приложения для чужих кабинетов (`S9`). Запасной вариант: инструкция владельцу, где получить `client_id` и `client_secret`, и защищённый ввод. Это хуже по удобству, но работает для уровня «прямой рекламодатель».
- Ограничение: не более пяти токенов на пару ключей, поэтому токены переиспользуем. **[Втор]**
- Включение опционально: каждая площадка имеет свой флаг; при сбое одной остальные работают.

**Условие начала:** Директ прошёл все сценарии приёмки. VK Реклама не должна ставить под угрозу основной результат.

## 6. Языковые и генеративные модели

| Порт | Использование |
|---|---|
| `TextModel` | Разбор бизнеса, концепции, объявления, объяснения, разбор команд |
| `ImageModel` | Фоны и сцены для креативов |
| `VideoModel` (необязателен) | Короткие сцены, если они прошли сравнение качества |

Требования: структурированный ответ с проверкой схемы, ограничения времени и стоимости, журнал стоимости. В модель не передаём ФИО, ИНН и токены. Провайдеры переключаются конфигурацией; при отказе показываем шаблон на реальных фото владельца, а не останавливаем запуск.

**Судья смысла и интернет.** Над кодом стоит судья-модель, которая проверяет смысл объявления по профилю и может только снять его (см. [креативы §7](05-creatives.md#7-что-реализовано)). Факты для рекламы берутся только из профиля бизнеса (инвариант). Интернет-агент допустим как источник фактов в профиль — читает сайт и карточки на картах, предлагает, владелец подтверждает, и только после этого факт попадает в профиль, — но не как судья, подтверждающий утверждения напрямую из сети: это нарушило бы инвариант, потому что страница бывает чужой, устаревшей или написанной нарочно. Такой режим — решение владельца (V2), в коде его нет.

**OpenRouter [проверено реальным вызовом 2026-11-01].** Адрес `https://openrouter.ai/api/v1`, без `OpenAI-Project`. Формат ответа выше записан с этого вызова. Ошибка провайдера приходит и под кодом 200 в поле `error`. Используется для судьи на тестовом ключе с лимитом 1$, модель `qwen/qwen3-30b-a3b-instruct-2507`. Ключ в незакоммиченном `.env`, в логи и модель не попадает.

**Один клиент OpenAI Chat Completions.** `POST <адрес>/chat/completions`, `Authorization: Bearer <ключ>`, тело с `model`, `messages`, `response_format={"type":"json_object"}`, `max_tokens`, `temperature=0`. В ответе `choices[0].message.content`, `choices[0].finish_reason` и `usage.total_tokens`. Ответ без `finish_reason=stop`, с пустым текстом или с полем `error` под кодом 200 считается отказом. Необязательный заголовок `OpenAI-Project` передаётся так же, как его отправляет OpenAI SDK. Переменные: `TEXT_MODEL_BASE_URL`, `TEXT_MODEL_API_KEY`, `TEXT_MODEL_PROJECT`, `TEXT_MODEL_NAME`, `JUDGE_MODEL_NAME`.

**Yandex AI Studio [Док, проверено 2026-11-01, реальным вызовом нет].** OpenAI-совместимый адрес `https://ai.api.cloud.yandex.net/v1`, каталог в заголовке `OpenAI-Project`, модель `gpt://<каталог>/yandexgpt/latest`, параметр `response_format` поддерживается. Источник: [базовый запрос](https://aistudio.yandex.ru/docs/en/ai-studio/operations/generation/completions-basic). Не подтверждено: в примере curl ключ передаётся как `Api-Key`, а не `Bearer`; `Bearer` следует из примера с OpenAI SDK. Поддержка `json_object` отдельно не описана. Старые документы называют адрес `llm.api.cloud.yandex.net/v1`. Всё это проверяет первый вызов. Прежний нативный адаптер `foundationModels/v1/completion` удалён.
