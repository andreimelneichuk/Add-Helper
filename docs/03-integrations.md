# Интеграции

Подтверждённые факты и ссылки находятся в [исследовании](00-research.md). Здесь — как мы их используем. `S1`–`S11` — открытые проверки из того же документа. Названия полей перед реализацией сверяются с актуальной документацией.

## 1. Яндекс ID

| Поток | Права | Назначение |
|---|---|---|
| Вход | `login:info`, `login:email` | Идентификация пользователя |
| Подключение кабинета | `direct:api`, `metrika:read`, `metrika:write` | Работа с рекламой и статистикой |

- Параметры приложения: `YANDEX_CLIENT_ID`, `YANDEX_CLIENT_SECRET`, `PUBLIC_BASE_URL`. Менять код не нужно.
- При подключении используем `force_confirm`, чтобы пользователь мог выбрать другой логин.
- Токены обновляются заранее. Истечение доступа создаёт проблему на главной и письмо (`S10`).
- Заголовок `Client-Login` передаётся, когда токен принадлежит представителю или агентству. Обычный сценарий: прямой рекламодатель.

## 2. Директ API

### Клиент

Собственный тонкий асинхронный клиент на `httpx`:
- Заголовки `Authorization`, `Accept-Language: ru`, при необходимости `Client-Login`.
- Разбор заголовка `Units`, сохранение остатка на аккаунт.
- Не более пяти запросов одновременно на рекламодателя, у нас по умолчанию два.
- Разделение ошибок: повторяемые, ошибки данных, авторизации, нехватка баллов.
- Запись запросов и ответов в служебный журнал без токенов и реквизитов.
- Версии маршрутов `v5` и `v501` заданы для каждого сервиса.

### Создаваемая структура

```text
Единая перфоманс-кампания (направление) [UNIFIED_CAMPAIGN, v501]
├─ Стратегия: максимум кликов, затем максимум конверсий с оплатой за клики
├─ Лимит: CustomPeriodBudget (S2)
├─ Метрика: CounterIds, PriorityGoals
├─ Группа: поисковые фразы по услуге + район
│   └─ 2–3 ResponsiveAd: заголовки, тексты, изображения, ErirAdDescription
├─ Группа: автотаргетинг и широкие интересы
└─ Группа: аудитории по интересам и географии
```

### Распределение

Количество направлений зависит от бюджета. Значения — стартовые гипотезы, их калибруем на этапе 1 и на реальных кампаниях.

| Бюджет в месяц | Структура |
|---|---|
| Ниже рекомендованного минимума | Предупреждаем. Одна кампания, поиск и сети, один главный оффер |
| Средний | Две кампании: поисковый спрос и сети, чтобы разделять и переносить бюджет |
| Выше | Поиск, сети и отдельная география; добавляется VK Реклама, если подключена |

Рекомендованный минимум считаем для ниши и региона: на него должно приходиться достаточно кликов для первых выводов. Источники: `Keywords` и прогноз `CreateNewForecast`, если они подойдут.

Стратегии: стартуем с оплаты за клики. `PayForConversion` не используем: дневной расход может доходить до 100% лимита, а минимум бюджета равен 20 × CPA. `WbMaximumConversionRate` включается от 10 конверсий в неделю (рекомендация Яндекса), смена проходит через проверку бюджета.

### Модерация

Состояния `DRAFT → MODERATION → ACCEPTED | REJECTED`. При отказе система получает причину, просит у модуля креативов исправление не более двух раз, затем передаёт понятную просьбу владельцу. Новое объявление начинает показы только после проверки, предыдущее работает дальше.

### Сверка статистики

Критерий заказчика: статистика совпадает с кабинетом. Что для этого делаем:

1. Показываем расход только из `Reports`, а не из расчётов.
2. Используем те же параметры, что и кабинет: `IncludeVAT`, `IncludeDiscount`, модель атрибуции (`S3`). В интерфейсе подписываем «с НДС» или «без НДС».
3. Округляем только при показе и по правилам кабинета.
4. Ежедневно перечитываем последние дни и обрабатываем сигнал `STAT`. Метка «данные могут уточниться» держится три дня.
5. Автоматическая сверка суммы по кампаниям с итогом по аккаунту. Различие попадает в служебную панель.
6. Точные настройки отчёта, для сравнения с кабинетом, описаны прямо на экране статистики.

## 3. Метрика

1. Найти счётчик: показать существующие или создать новый.
2. Создать цели: заявка, клик по телефону, переход в мессенджер, запись. Часть целей срабатывает автоматически, а для заявок даём код `reachGoal`.
3. Проверка установки: загрузка страницы сайта и поиск кода, затем подтверждение поступления визитов через API.
4. Привязка к кампании через `CounterIds` и `PriorityGoals`.
5. Роли целей: `lead` (обращение) и `micro` (сигнал для коротких тестов, например переход к форме).
6. Отчёт по обращениям берётся из `Reports` (колонка конверсий по цели и модели) для сопоставления с расходом. Метрика используется как перекрёстная проверка (`S11`).

Настройка должна укладываться в квоты: 200 запросов отчётов за 5 минут на пользователя, 5000 в сутки.

## 4. Маркировка

**Директ, прямой рекламодатель**
1. На шаге онбординга собираем тип, ИНН, наименование или ФИО, телефон для физлиц, ОКВЭД.
2. Проверяем контрольную сумму ИНН и сохраняем в зашифрованном виде.
3. Отправляем `Clients.update` (`TinInfo`, `ErirAttributes`), перечитываем и сверяем.
4. В каждом объявлении заполняем `ErirAdDescription`: бренд, категория, суть. До 1000 символов.
5. Проверка данных блокирует запуск: «Без этих данных запустить рекламу нельзя по закону».
6. Показываем правило: один логин — один бизнес — один плательщик. Иначе требуется кабинет ОРД, и это выходит за рамки автоматического сценария.

Токен и пометка «Реклама» для Директа присваиваются автоматически. Проверим фактическое появление на боевом объявлении.

**VK Реклама:** порядок определяется проверкой `S9`.

## 5. VK Реклама (вторая площадка, этап 6)

- Адаптер того же порта `AdPlatform`. Отображение: `AdPlan → кампания`, `AdGroup → группа`, `Banner → объявление`.
- Подключение. Предпочтительно OAuth сервисного приложения для чужих кабинетов (`S9`). Запасной вариант: инструкция владельцу, где получить `client_id` и `client_secret`, и защищённый ввод. Это хуже по удобству, но работает для уровня «прямой рекламодатель».
- Ограничение: не более пяти токенов на пару ключей, поэтому токены переиспользуем. **[Втор]**
- Включение опционально: каждая площадка имеет свой флаг; при сбое одной остальные работают.

**Условие начала:** Директ прошёл все сценарии приёмки. VK Реклама не должна ставить под угрозу основной результат.

## 6. Языковые и генеративные модели

| Порт | Использование |
|---|---|
| `TextModel` | Разбор бизнеса, концепции, объявления, объяснения, разбор команд |
| `ImageModel` | Фоны и сцены для креативов |
| `VideoModel` (необязателен) | Короткие сцены, если они прошли сравнение качества |

Требования: структурированный ответ с проверкой схемы, ограничения времени и стоимости, журнал стоимости. В модель не передаём ФИО, ИНН и токены. Провайдеры переключаются конфигурацией; при отказе показываем шаблон на реальных фото владельца, а не останавливаем запуск.
