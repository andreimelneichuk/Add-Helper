# Задача 05. Нативное A/B-тестирование внутри групп объявлений Директа

- **Приоритет:** P1 (Важный)
- **Сложность:** Средняя (Medium)
- **Трудозатраты с Claude Code:** 0.5–1 рабочий день (1 сессия вместо 3–4 дней у человека)
- **Зависимости:** Задача 01 (Direct API)
- **Блокирует:** Задача 09

---

## 1. Проблема
Текущая модель A/B-тестирования опирается на последовательность Морса (Thue-Morse) и чередует варианты A и B посуточно через `pause_ad` / unpause.
В реальном Директе:
1. Ежедневное выключение/включение объявлений сбивает обучение умных стратегий автотаргетинга и вызывает повторные задержки модерации/разогрева.
2. При малом трафике микробизнеса (10–15 кликов в день) раздельное накопление данных займет месяцы.

## 2. Что нужно сделать

1. **Перейти к нативному сплиту внутри одной группы объявлений:**
   - Внутри одной группы объявлений (`AdGroup`) создавать одновременно 2 (или 3) активных варианта с разными гипотезами (разный заголовок, разный текст, разная картинка).
   - Директ самостоятельно рандомизирует и распределяет показы между объявлениями одной группы в реальном времени без сбивания автостратегий.
2. **Анализ результатов через периодический воркер:**
   - Воркер раз в сутки читает отчет `Reports` с детализацией по `AdId`.
   - После набора минимального числа кликов (например, от 50–100 кликов на группу) вычисляется Байесовская вероятность победы варианта B над вариантом A (`probability_b_better`).
   - Если один вариант достоверно побеждает с порогом уверенности $\ge 80\%$, проигравший вариант переводится в статус `lost_test` и ставится на паузу (`AdControl.set_ad_active(..., False)`).
3. **Обновление симулятора и правил (`experiments-1.toml`):**
   - Актуализировать пороги минимального объема данных с учетом параллельного нативного теста.
